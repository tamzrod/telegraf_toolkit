# Project context

Status: Phase 0/1/2 scaffolds implemented; the operational Phase 2 Registry backend (P2L-001–P2L-007) merged into `main` via PR #6 on 2026-10-21, and the Phase 2 completion workstream (P2C-001–P2C-008) merged via PR #7. Phase 3 documentation reconciliation, the authorized measurement-level read path (P3-002) and the read-only Canonical Mapper schema browser (P3-003) are implemented (2026-10-26); no mapping draft, canonical-schema persistence or export exists yet, and InfluxDB 1.x remains unverified. P3-003 is checkpointed on `phase-3/canonical-mapper`, not merged.

Telegraf Toolkit is a browser-based management/control plane for official Telegraf runtimes, visual configuration, a dual-database canonical mapper, reusable connection/credential registry, and independent cross-version InfluxDB historical synchronization.

**Authority:** `IDENTITY.md`. Detailed contracts remain in `docs/`. The Go backend and React SPA scaffolds exist; the Registry backend persists profile, credential-reference, audit and ciphertext-envelope metadata in SQLite (ADR-0002, `docs/METADATA_STORE.md`), stores credential values as authenticated envelopes with keys held in a separate file (ADR-0003, `docs/SECRET_STORE.md`), serves an authorized HTTP surface with role-based permissions and an administrator-only credential attachment binding (`docs/REGISTRY_API.md`), performs read-only live capability probing with pinned-peer/SSRF controls (`docs/LIVE_PROBING.md`) and is listed by the Databases UI from the live API (`docs/LIVE_UI.md`). Authentication is static file-provisioned bearer tokens; capability outcomes are projected from observations against the detected edition; a credential replacement requires a protected, read-only authorization proof and a compare-and-swap swap, revocation refuses while anything still references the credential (P2C-007), and replacement, enrollment and revocation commit through one SQLite lifecycle transaction that re-checks the active reference, approved binding and profile endpoint/scope before the envelope write, so a concurrent revocation, rebinding, profile deletion or enrollment fails the replacement closed (P2C-008); InfluxDB 1.x is unverified. Phase 3 has an implemented read path and a read-only browser but no mapping: P3-002 delivered the approved Option A1 measurement-level read (`GET /api/v1/registry/schema/{measurements,fields,tags}` under `schema.read`) executing only fixed GET `SHOW` statements with bounded timeouts/caps/truncation, membership validation and redacted audit, verified against the pinned InfluxDB 2 OSS v2.9.1 / 3 Core v3.12.1 containers; the approved P2C-003 v3 catalogue correction is implemented. P3-003 delivered the Canonical Mapper schema browser: explicit distinct source/destination selection, typed measurement/field/tag groups over that read path, distinct loading/empty/permission/unknown/unsupported/truncated/stale states, labeled Mock mode with no live fallback, and cache cancellation on selection/token/mode changes. Mapping drafts, validation, canonical-schema versioning/export and InfluxDB 1.x coverage remain unimplemented/unverified.

**Boundaries:** No managed Telegraf fork, no floating versions, no direct browser privileged credentials/Docker access, no implicit deployment or historian repair, and no count-match equivalence claim. The metadata store holds credential references and ciphertext; plaintext values and keys never enter it. The browser ships live listing, read-only probing, profile create/delete, the administrator-only credential lifecycle (P2C-004–P2C-008) and the read-only Canonical Mapper schema browser (P3-003); runtime secret delivery, usage/dependency inspection, browser master-key rotation and mapping drafts/persistence remain unimplemented.

**Open decisions:** host-agent interface, production packaging and concrete adapters. Preserve these as unresolved. (Metadata store and secret-store custody were decided in ADR-0002/ADR-0003.) The Phase 3 measurement-level read path was decided on 2026-10-26 (Option A1: bounded GET-only fixed `SHOW` statements under a dedicated `schema.read`), approved, and implemented by P3-002 (`docs/decisions/phase-3-schema-discovery-gate.md` §11).
